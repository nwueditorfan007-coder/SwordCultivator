# 当前操作与剑阵实现还原

记录日期：2026-05-13

本文只还原当前代码中 `res://scenes/main/Main.tscn` 实际运行的操作、瞄准、御剑和剑阵实现。它不是后续设计定案，也不替代 `docs/decisions/PROJECT_DECISIONS.md`。如果本文与定案文档冲突，应理解为“当前实现状态”和“目标方向”不同。

## 1. 代码依据

- 主入口：`project.godot` 指向 `res://scenes/main/Main.tscn`
- 主状态机：`scripts/system/main.gd`
- 初始状态构建：`scripts/system/game_state_factory.gd`
- 剑阵形态与参数：`scripts/system/sword_array_config.gd`
- 剑阵几何、发射目标和槽位：`scripts/system/sword_array_controller.gd`
- 剑阵带状几何：`scripts/system/sword_array_band_family.gd`
- 渲染与光标意图反馈：`scripts/system/game_renderer.gd`
- 伤害配置：`scripts/combat/attack_profiles.gd`

`scripts/player/player.gd` 和 `scripts/player/flying_sword.gd` 是独立的节点式玩家/飞剑脚本，但当前主场景没有把 `scenes/player/Player.tscn` 作为核心玩家实体使用。当前主玩法应以 `scripts/system/main.gd` 中的字典状态机为准。

## 2. 当前游戏视角与空间模型

当前主玩法是单屏俯视角动作弹幕原型，不是第一人称或第三人称跟随相机。

- 视口配置为 `1280 x 720`
- 实际战斗区域为 `800 x 600`
- 战斗区域原点为屏幕坐标 `(240, 72)`
- 世界坐标与屏幕坐标之间只做固定偏移转换，没有摄像机旋转、视角俯仰或镜头跟随
- 玩家在战斗区域内移动，位置被限制在 arena 边界内

鼠标在运行中被转换为 `mouse_world`。当前游戏内鼠标更接近一个“俯视角世界光标/剑意指向点”，而不是 FPS 的屏幕中心准星。

当前代码在正常战斗中使用虚拟鼠标运动：

- 鼠标移动时，`mouse_world += event.relative`
- `mouse_world` 被限制在战斗区域内
- 菜单、Lookdev、Game Over 状态下才更多使用屏幕位置换算

这意味着当前瞄准不是“屏幕中心不动、镜头转动”，而是“鼠标点在世界平面上移动”。

## 3. 基础输入职责

当前输入职责如下：

| 输入 | 当前职责 |
| --- | --- |
| `WASD` | 玩家平面移动 |
| 鼠标移动 | 控制 `mouse_world`，同时影响近战朝向、御剑目标、剑阵方向、距离控阵 |
| 左键点按 | 飞剑在身边时触发近战挥剑 |
| 左键长按约 `0.10s` | 进入并维持剑阵持续发射 |
| 右键按下 | 如果御剑已解锁且飞剑在身边，立即进入御剑连斩预备/连斩态 |
| 右键快速松开 | 将当前御剑动作转为点刺 |
| 右键长按后松开 | 御剑从连斩态回收 |
| `Space` | 只在 `Space切阵` 操作方案下循环切换剑阵形态；默认距离控阵方案下不承担战斗功能 |
| `F6` | 剑阵距离校准调试 |
| `F7` | 战斗调试 |

当前最容易造成讨论误差的一点是：右键并不是“松开后才开始御剑”。代码里右键按下时已经调用 `_start_slicing()`，短按松开时再转成 `_commit_quick_release_point_strike()`。

## 4. 玩家移动和近战

玩家移动由 `Input.get_vector("move_left", "move_right", "move_up", "move_down")` 得到方向，速度为 `PLAYER_SPEED = 300`。没有冲刺、翻滚或相机相对移动。

飞剑处于 `ORBITING` 时，玩家处于近战态：

- 飞剑在玩家身边，朝向由 `mouse_world - player.pos` 决定
- 左键按下会触发近战段数
- 近战方向同样来自鼠标指向
- 近战可以造成伤害、弹反子弹、回复剑意
- 飞剑在身边时玩家自然回复少量剑意

所以当前近战不是锁定目标式，也不是移动方向式，而是鼠标方向式。

## 5. 当前御剑实现

御剑使用同一把主飞剑，状态枚举包括：

- `ORBITING`：飞剑在玩家身边，近战态
- `SLICING`：右键按住后，飞剑持续追随鼠标切割
- `POINT_STRIKE`：短按右键后，飞剑刺向目标点
- `PIERCE_DRAWING`：特定共鸣连招中的画线蓄势态
- `RECALLING`：飞剑回收至玩家身边

实际流程：

1. 飞剑在 `ORBITING` 时，右键按下。
2. 代码记录 `right_mouse_held = true`，清零 `press_timer`，把 `target_pos` 设为 `mouse_world`。
3. 立即调用 `_start_slicing()`，进入御剑态并触发时裂/子弹时间表现。
4. 如果右键很快松开，且当前仍处于 `SLICING`，并且 `press_timer < 0.15s`，则转为点刺。
5. 如果右键长按，`SLICING` 中飞剑不断 lerp 到 `mouse_world`，形成拖拽切割。
6. 松开长按后，飞剑进入 `RECALLING`，按回收速度飞回玩家身边。
7. 回到玩家身边后状态变回 `ORBITING`，玩家回到近战态。

御剑期间会触发时间缩放：

- 敌方弹幕从 `0.2x` 逐渐恢复到 `1.0x`
- 玩家从 `0.85x` 逐渐恢复到 `1.0x`
- 特定贯穿共鸣画线时，敌方弹幕可降到 `0.06x`

因此当前御剑的核心感觉是“鼠标拖拽世界中的飞剑”，不是“角色向准星发射一枚投射物”。这点应被视为当前核心御剑感。

## 6. 当前剑阵库存

当前剑阵不是临时特效，也不是吸收弹幕后生成的库存。代码中固定维护 `ARRAY_SWORD_COUNT = 12` 把剑阵飞剑。

每把剑阵飞剑是一个字典状态，核心字段包括：

- `state`：`ready`、`outbound`、`returning`
- `slot_index`：在当前阵型中的槽位
- `travel_mode`：本次出击使用的形态语义
- `guidance_active`：短时间制导是否仍有效
- `guidance_distance`：本次已飞行距离
- `remaining_penetration`：剩余可命中目标数
- `batch_id`：扇阵同批回收用

飞剑生命周期：

1. `ready`：在玩家周围按当前阵型槽位排列。
2. 左键长按进入剑阵后，从 ready 飞剑里选出一批发射。
3. 发射后变为 `outbound`，带攻击实例和短时间制导。
4. 命中、达到最小出击距离、达到最大距离或离开边界后进入回收。
5. 回到槽位附近后变回 `ready`。

这意味着玩家看到的剑阵飞剑既是视觉实体，也是可用库存。场上缺口本身就是系统读感的一部分。

## 7. 剑阵操作方案

当前代码支持两套剑阵操作方案。

### 7.1 默认方案：距离控阵

默认值是 `distance_aim`，界面显示为“距离控阵”。

在这个方案下：

- 鼠标离玩家近：环阵
- 鼠标在中距离：扇阵
- 鼠标远离玩家：贯穿阵

关键距离来自 `SwordArrayConfig`：

| 阶段 | 距离 |
| --- | ---: |
| 环阵稳定结束 | `85` |
| 环到扇过渡结束 | `145` |
| 扇阵稳定结束 | `295` |
| 扇到贯穿过渡结束 | `400` |

代码将剑阵状态分成两层：

- 视觉层：使用原始鼠标距离 `array_raw_aim_distance`
- 发射层：使用平滑后的 `array_control_distance`

发射层还使用更宽的控制阈值，减少持续发射时因为鼠标轻微抖动导致误切形态。代码还对 `dominant_mode` 做了滞后处理，让上一个主导形态不会在过渡段里过快跳变。

### 7.2 备用方案：Space切阵

代码里仍保留 `space_toggle`，界面显示为“Space切阵”。

在这个方案下：

- `Space` 在已解锁的环阵、扇阵、贯穿阵之间循环
- 鼠标距离不再决定形态
- 鼠标仍然决定方向、目标点和剑阵朝向
- 形态状态被锁到对应形态的规范距离比例

这套方案当前存在于代码和操作说明里，但项目定案文档明确写着“不使用滚轮切换阵型”“阵型主导语义仍由准星与玩家距离决定”。因此它应被理解为当前代码支持的操作实验，而不是已经确认的最终方向。

## 8. 左键剑阵启动与维持

当前剑阵由左键长按进入，阈值为 `SwordArrayConfig.HOLD_THRESHOLD = 0.10s`。

触发条件：

- 左键保持按下
- 持续时间超过 `0.10s`
- 至少解锁了对应剑阵形态
- 当前形态需要的 ready 飞剑数量足够
- 剑意足够支付本轮发射成本

当条件满足时：

1. `_begin_sword_array_firing()` 将 `array_is_firing` 设为 true。
2. 立即尝试 `_fire_array_swords()`。
3. 之后 `_update_sword_array_continuous_firing()` 按释放频率持续发射。
4. 左键松开、剑意不足、未解锁或条件不足时会重置剑阵持续状态。

当前剑阵仍是日常可用的常规输出位，并且消耗剑意；它还不是只在强化窗口中出现的爆发层。

## 9. 三种剑阵形态的代码职责

### 9.1 环阵

环阵的代码身份是近身守身与解压。

- 槽位：围绕玩家成环
- 发射批量：当前容量整批，通常为 `12`
- 发射间隔参数：`0.30`
- 每把消耗剑意：`0.95`
- 出击距离较短
- 命中半径补正最大
- 穿透目标数：`1`
- 持续剑阵期间，环阵可清理玩家附近或环阵飞剑附近的普通子弹

环阵的发射方向更多来自飞剑相对玩家的径向位置，而不是全部强行朝鼠标点直射。它更像把已有护身环向外推出一圈。

### 9.2 扇阵

扇阵的代码身份是中距离面扫。

- 槽位：朝鼠标方向展开的扇面/带状区域
- 发射批量：容量一半，通常为 `6`
- 发射间隔参数：`0.16`
- 每把消耗剑意：`1.00`
- 同批飞剑共享 `batch_id`
- 同批飞剑都准备回收后，再一起回收
- 穿透目标数：`1`

扇阵强调同批扫面和节奏感，而不是逐把点杀。

### 9.3 贯穿阵

贯穿阵的代码身份是远距离破线。

- 槽位：沿鼠标方向收束成线/楔形
- 发射批量：逐把发射
- 发射间隔参数：`0.08`
- 每把消耗剑意：`1.10`
- 最大出击距离最长
- 制导距离最长
- 命中半径补正最小
- 穿透目标数：`4`

贯穿阵是当前三形态里最接近“精确瞄准奖励”的形态，但它仍然从剑阵槽位和玩家身边的实体飞剑出发，不是屏幕中心发枪。

## 10. 剑阵几何与连续变形

当前三形态都属于 `band` 阵型族。

形态不是三套完全断开的图形，而是由 `SwordArrayConfig` 中的 preset 和 morph profile 连续过渡：

- `guard_band`：环阵/护身带
- `pressure_band`：扇阵/压制带
- `pierce_band`：贯穿带

距离控阵时：

- 近距离直接使用环阵状态
- `85 -> 145` 之间从环阵过渡到扇阵
- `145 -> 295` 之间稳定扇阵
- `295 -> 400` 之间从扇阵收束到贯穿阵
- 超过 `400` 后稳定贯穿阵

渲染层会在左键蓄阵超过约 `0.08` 后画阵型预览。未蓄阵时也有较弱的常驻阵型存在感，用于表达 12 把飞剑的库存和当前鼠标意图。

## 11. 鼠标/光标意图反馈

当前鼠标视觉不是普通系统光标。`GameRenderer` 会绘制一套“cursor intent indicator”：

- 根据当前剑阵形态变成环、扇、贯穿三种小图形
- 鼠标快速移动时有速度反馈
- 形态切换时有确认反馈
- 剑阵发射时有脉冲反馈
- 剑意不足或距离过远时有状态覆盖
- 近身压力未被当前瞄准/形态覆盖时会有压力提示

这套系统说明当前代码已经在尝试把鼠标做成“战斗意图指示器”，而不是单纯的 UI 光标。后续如果讨论“更偏 FPS”，应优先讨论这套意图反馈是否要更稳定、更集中、更像准星，而不是直接改成 FPS 相机。

## 12. 当前解锁节奏

代码中的能力解锁波次：

| 能力 | 波次 |
| --- | ---: |
| 近战 | 默认可用 |
| 御剑 | `2` |
| 环阵 | `3` |
| 扇阵 | `4` |
| 贯穿阵 | `5` |

未解锁时，输入会被拦截，并显示对应失败反馈，例如“御剑未解锁”“环阵未解锁”等。

## 13. 与后续讨论相关的关键结论

从代码看，当前玩家的操作负担主要来自同一个鼠标点同时承担多重职责：

- 它决定近战挥剑方向
- 它决定右键御剑目标和连斩路径
- 它决定剑阵朝向
- 默认方案下，它还通过“与玩家距离”决定剑阵形态
- 它还承载光标意图 UI、距离提示、压力提示和资源提示

因此，如果后续讨论“让操作模式更偏 FPS”，更准确的问题不是“是否改成第一人称射击”，而是：

1. 是否要把鼠标从“世界平面光标”改成更稳定的“瞄准焦点”？
2. 是否要减少鼠标距离同时承担“目标距离”和“形态选择”的双重职责？
3. 御剑的拖拽飞剑感是否必须完整保留？
4. 剑阵变形是继续由鼠标距离驱动，还是需要更明确的确认/预读/锁定反馈？
5. 贯穿阵是否应该成为最吃精确瞄准的形态，而环阵和扇阵继续服务空间控制？

这些问题应建立在当前实现之上讨论，避免把“御剑拖拽实体飞剑”的核心手感误改成“准星发射子弹”。
